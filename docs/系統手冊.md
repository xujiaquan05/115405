# 第 1 章　前言

## 1-1　背景介紹

臺灣醫學美容市場近年快速成長，療程種類（音波拉皮、電波、玻尿酸、肉毒桿菌素、雷射）與診所數量同步增加。消費者在決定是否接受療程前，習慣先到網路社群蒐集他人經驗，主要集中在 PTT（BeautySalon、facelift 等看板）、Dcard、Mobile01 與 Threads。

這些討論具有三項特徵，使其難以用人工方式掌握：

1. **分散**：同一個療程的討論散落在四個平台、數十個看板。
2. **高頻**：熱門看板每日新增數十篇文章與數百則留言。
3. **關鍵資訊在留言**：發文者的提問往往中性，真正的評價（推薦或勸退）出現在底下的推文與留言。

對診所端而言，負面討論若未在擴散前被發現，往往在形成聲量後才被動應對；對消費者端而言，要在上千篇文章中找到與自己情況相符的經驗，成本極高。

## 1-2　動機

本專題的動機來自一個具體觀察：現有的社群搜尋只能做**字面比對**。使用者若搜尋「填充物」，搜不到寫「玻尿酸」的文章；搜尋「除皺針」，搜不到寫「肉毒」的文章——儘管談論的是同一件事。

本系統實測資料可以量化這個落差：資料庫中 9,852 篇文章裡，「除皺針」一詞出現 **0 次**，但討論肉毒的文章有 **139 篇**。純關鍵字檢索對這個問題的回答是「查無資料」。

因此，本專題希望建立一套系統，同時具備三項能力：

- 自動、定時地從四個平台蒐集醫美相關討論。
- 以大型語言模型判讀情緒，而非僅依賴推文數等間接指標。
- 以**語意檢索**回答自然語言問題，讓用詞不同也能找到相關討論。

## 1-3　系統目的與目標

**系統目的**：提供醫美產業的品牌方與行銷人員一套可持續運作的輿情監測工具，把分散在社群平台的討論轉換為可判讀的指標與可追問的知識庫。

**具體目標**：

| 目標 | 衡量方式 |
| --- | --- |
| 跨平台自動蒐集 | 支援 PTT／Dcard／Mobile01／Threads 四個平台 |
| 情緒判讀涵蓋率 | 文章情緒評分涵蓋率達 100% |
| 語意檢索能力 | 用詞不同的問題仍能檢索到相關文章 |
| 主動預警 | 負面聲量超過門檻時自動產生警示 |
| 無人值守運作 | 每日定時自動執行，不需人工觸發 |

# 第 3 章　系統規格

## 3-1　系統架構

系統採前後端分離架構，後端再依職責分為 API 層、服務層與資料層。

**圖 3-1　系統架構圖**

```mermaid
flowchart TB
    subgraph CLIENT["使用者端"]
        BROWSER["瀏覽器<br/>Vue 3 SPA"]
    end

    subgraph SERVER["應用伺服器（FastAPI）"]
        API["API 層<br/>11 個 router／43 個端點"]
        SVC["服務層<br/>21 個 service 模組"]
        CRAWL["爬蟲層<br/>4 個平台爬蟲"]
        SCHED["排程器<br/>APScheduler"]
    end

    subgraph DATA["資料層"]
        PG[("PostgreSQL 18<br/>19 張資料表")]
    end

    subgraph EXT["外部服務"]
        GEMINI["Google Gemini<br/>對話模型／向量模型"]
        SITES["PTT／Dcard<br/>Mobile01／Threads"]
    end

    BROWSER -- "HTTPS / WebSocket" --> API
    API --> SVC
    SVC --> PG
    SVC --> GEMINI
    SCHED --> CRAWL
    API --> CRAWL
    CRAWL --> SITES
    CRAWL --> PG
```

**反爬蟲的處理方式**：四個平台的取得難度不同，因此採用兩種策略。

| 平台 | 阻擋機制 | 因應方式 |
| --- | --- | --- |
| PTT | 無（僅需 over18 cookie） | `requests` + BeautifulSoup |
| Dcard | Cloudflare 阻擋無頭瀏覽器 | Playwright 真實瀏覽器 + 攔截 API 回應 |
| Mobile01 | Akamai 依 TLS 指紋阻擋一般 HTTP 請求（回 403） | Playwright 真實瀏覽器 |
| Threads | 內容由 JavaScript 動態渲染 | Playwright 真實瀏覽器 |

**圖 3-2　資料處理管線**

```mermaid
flowchart LR
    A["取得原始資料"] --> B["相關性過濾"]
    B --> C["寫入資料庫<br/>unique_id 去重"]
    C --> D["Gemini 情緒評分<br/>文章與留言"]
    D --> E["切段產生語意向量"]
    E --> F["關鍵字監測<br/>與預警判斷"]
```

相關性過濾在**寫入資料庫之前**執行：PTT 採看板加權，Dcard／Mobile01／Threads 因內容較生活化，改採關鍵字門檻（標題命中權重 3、內文權重 1，需達 2 分）。此設計使資料庫不被無關文章污染，後續分析的輸入較乾淨。

## 6-1　循序圖

### 6-1-1　使用者登入

**圖 6-1　循序圖：使用者登入**

```mermaid
sequenceDiagram
    actor U as 使用者
    participant V as LoginView (Vue)
    participant R as auth router
    participant A as auth_service
    participant D as PostgreSQL
    participant AU as audit_service

    U->>V: 輸入帳號密碼
    V->>R: POST /api/auth/login
    R->>A: authenticate_user()
    A->>D: 查詢使用者
    D-->>A: User

    alt 帳號已鎖定
        A-->>R: LoginResult(locked)
        R->>AU: 記錄鎖定事件
        R-->>V: 423 帳號暫時鎖定
    else 密碼錯誤
        A->>D: failed_login_count + 1
        Note over A,D: 達 5 次則設定 locked_until
        A-->>R: LoginResult(invalid)
        R->>AU: 記錄登入失敗
        R-->>V: 401 帳號或密碼錯誤
    else 驗證成功
        A->>A: 檢查是否需重新雜湊
        opt 迭代次數過舊
            A->>D: 以 600,000 次迭代更新雜湊
        end
        A->>D: 清空失敗次數、更新 last_login_at
        A-->>R: LoginResult(ok, User)
        R->>R: 簽發 JWT
        R-->>V: Set-Cookie (httpOnly, SameSite=strict)
        V-->>U: 導向儀表板
    end
```

**設計說明**：

- **漸進式重新雜湊**：迭代次數提高後，既有帳號不需要求使用者重設密碼；在下次登入成功、已知明文的瞬間就地升級。
- **權杖失效**：JWT 的簽發時間（`iat`）與 `users.password_changed_at` 比對，變更密碼後舊權杖一律失效。此比較保留微秒精度——若兩邊都截到秒，同一秒內完成的變更會比不出先後，功能形同無效。

### 7-4-1　爬取鎖狀態機

爬取鎖是系統中最關鍵的並行控制機制。其狀態轉移設計解決了三個實際遇到的問題：多工作行程各持一份旗標、持鎖行程被強制關閉後鎖永久卡住、以及 TTL 短於爬取時間導致鎖在爬取中途過期。

**圖 7-4　狀態機：爬取鎖**

| 子表.欄位 | 參考 | 刪除規則 | 設計理由 |

| `articles.platform_id` | `platforms.id` | NO ACTION | 已蒐集的文章為歷史資料，不隨平台設定刪除而消失 |
| `articles.board_id` | `boards.id` | NO ACTION | 同上 |

| `usage_counters.user_id` | `users.id` | CASCADE | 同上 |

| `watch_keywords.user_id` | `users.id` | CASCADE | 個人化設定隨帳號刪除 |
| `alerts.user_id` | `users.id` | CASCADE | 同上 |
| `audit_logs.actor_id` | `users.id` | SET NULL | **刻意不用 CASCADE**：帳號被刪除時正是最需要保留稽核紀錄的時候，`actor_username` 另存一份名稱，連結斷了仍可追查 |
| `users.plan_code` | `plans.code` | RESTRICT | 還有帳號在用的方案不可刪除；CASCADE 會連帶刪掉使用者，SET NULL 會讓帳號沒有方案 |

> **補充說明**：上表後四組外鍵原本只存在於 SQLAlchemy 模型，資料庫並未建立。
> 原因是這些欄位是在資料表已存在後以 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 補上的——
> `ADD COLUMN` 只加欄位不建外鍵，而 `create_all` 只建立缺少的**資料表**，不會在既有資料表上補約束。
> 已於遷移 `e4f70c2a9d18` 補齊，補之前先確認資料庫中沒有孤兒列。

**唯一性限制**：

- `articles.unique_id`：以「平台:看板:網址」雜湊產生，是重複爬取時判斷文章是否已存在的依據。
- `article_chunks (article_id, chunk_index)`：複合主鍵，確保同一篇文章的同一段落不會重複寫入。
- `platforms.name`、`users.username`：唯一。

**索引設計**：

| 索引 | 對象 | 用途 |
| --- | --- | --- |
| `idx_articles_title_trgm` | `articles.title` | pg_trgm GIN，支援中文 `ILIKE '%詞%'` 查詢 |
| `idx_articles_content_trgm` | `articles.content` | 同上 |
| `ix_articles_sentiment` | `articles.sentiment` | 情緒分佈統計 |
| `ix_comments_article_id` | `comments.article_id` | 取得文章留言 |

> **設計取捨**：中文無空白分詞，PostgreSQL 內建的 `to_tsvector` 全文檢索無法正確切詞，因此改用 pg_trgm 三連字元索引。其限制是查詢詞需達 3 個字以上才能使用索引；兩字詞（如「音波」）仍為全表掃描，但在套用時間範圍後候選數已降至數百至一千餘篇，實測仍在百毫秒內完成。

| `model` | varchar(50) | NO | - | 產生此向量的模型名稱 |
| `dimensions` | integer | NO | - | 向量維度（768） |
| `vector` | bytea | NO | - | float32 小端序，長度為 dimensions × 4 bytes |
| `created_at` | timestamp | YES | now() | 產生時間 |

> **設計取捨**：本機 PostgreSQL 未安裝 pgvector 擴充，故以 bytea 儲存 float32 位元組，讀出後直接由 NumPy 解讀。實測全庫 9,702 段向量的精確餘弦計算僅需 36 毫秒，而查詢總時間 1.7 秒中絕大部分是「將問題轉為向量」的 API 呼叫——該成本與資料量無關。在此規模下，近似最近鄰索引能縮短的正是那 36 毫秒，因此精確計算既較快也較準確。日後若資料量成長至百萬級，改用 pgvector 僅需修改此欄位型別與查詢函式。

## 10-5　檢索品質驗證

為驗證語意檢索確實補足關鍵字檢索的不足，設計對照實驗（可由 `scripts/compare_retrieval.py` 重現）：

**實驗一：關鍵字完全無字面命中**

問題「除皺針打了會有什麼副作用」，「除皺針」一詞在 9,852 篇文章中出現 0 次。

| 檢索方式 | 結果篇數 | 前三名 |
| --- | --- | --- |
| 關鍵字檢索 | **0 篇** | — |
| 語意檢索 | **12 篇** | 打完肉毒眼睛變小／針劑補全臉後表情僵硬／肉毒打完眼睛吊吊的 |

**實驗二：切段對長文的影響**

問題「外泌體是從哪裡來的，植物來源跟動物來源差在哪」，目標為一篇 6,774 字的長文，相關內容位於第 1,600 字左右。

| 文章表示法 | 相似度 | 排名 |
| --- | --- | --- |
| 切段後（命中的那一段） | 0.6970 | 第 3 名 |
| 切段前（整篇一個向量、僅取前 1,000 字） | 0.5904 | 掉出前 6 名 |

> 同一排名中其餘文章皆短於 1,000 字，其新舊表示法為同一段文字、分數不變，故此對照成立。
> 值得注意的是「外泌體」一詞本就位於前 1,000 字內——舊作法並非搆不到該主題，而是一個向量需代表 6,774 字的多個主題而被稀釋。

系統初始化會建立預設管理員帳號。**首次登入後必須立即於「帳號資訊 → 修改密碼」變更密碼**；系統已將預設密碼列入黑名單，無法沿用。

### 11-3-2　系統設定項目

於「系統管理 → 系統設定」調整，變更後即時生效、不需重啟：

| 設定 | 預設值 | 說明 |
| --- | --- | --- |
| `auto_crawl_enabled` | 開啟 | 每日自動爬取總開關 |
| `auto_crawl_hour` | 3 | 每日執行時間（台灣時間） |
| `auto_crawl_pages` | 2 | 每個看板爬取頁數 |
| `startup_catchup_enabled` | 開啟 | 啟動時若當日尚未執行則補跑一次 |
| `dcard_crawl_enabled` | 開啟 | 無頭環境應關閉 |
| `mobile01_crawl_enabled` | 開啟 | 同上 |
| `threads_crawl_enabled` | 開啟 | 同上 |
| `alert_warning_negative` | 25 | 負面比例警示門檻（%） |
| `alert_critical_negative` | 40 | 負面比例嚴重門檻（%） |
| `alert_min_articles` | 5 | 觸發預警所需的最少文章數 |

### 11-3-3　資料維護作業

| 作業 | 指令 | 時機 |
| --- | --- | --- |
| 補情緒評分 | `python scripts/backfill_sentiment.py` | 匯入舊資料後 |
| 補語意向量 | `python scripts/backfill_embeddings.py` | 匯入舊資料或更換向量模型後 |
| 預覽作業量 | 加上 `--dry-run` | 執行前確認 API 呼叫次數 |
| 檢索品質驗證 | `python scripts/compare_retrieval.py` | 調整檢索邏輯後 |

### 11-3-4　常見狀況處理

| 現象 | 原因 | 處理方式 |
| --- | --- | --- |
| 前端顯示「請確認網路或 backend 狀態」 | 後端未啟動或未回應 | 確認 uvicorn 是否執行、8000 埠是否被佔用 |
| 日誌出現 `Taking over expired lock` | 前次持鎖的行程異常結束 | 正常的保護機制，無需處理 |
| 爬取回應「已有爬取進行中」 | 互斥鎖生效 | 等待前次完成，或於爬取管理頁重設 |
| 排程未執行 | 主機於排程時間未開機 | 啟用 `startup_catchup_enabled` |
| 無頭環境爬取失敗 | 無法開啟瀏覽器 | 於系統設定關閉三個瀏覽器型平台 |

## 12-2　各畫面操作說明

### 12-2-1　首頁

系統介紹頁，說明功能特色、運作流程與常見問答。提供兩個入口：「登入系統」與「以訪客身分瀏覽 Dashboard」。已登入時按鈕改為「進入 Dashboard」。

### 12-2-2　登入

輸入帳號與密碼後登入。連續輸入錯誤 5 次，帳號將鎖定 15 分鐘；此期間即使輸入正確密碼亦無法登入。

### 12-2-3　輿情儀表板

畫面分為四區：

1. **統計卡片**：文章總數、平均互動數、負面文章數。
2. **聲量趨勢**：每日文章數折線圖。
3. **情緒分佈**：正面／中性／負面圓餅圖。
4. **來源平台**：各平台佔比。
5. **熱門文章**：依互動數排序，點選進入詳情。

上方可依**關鍵字**、**時間範圍**與**平台／看板**篩選，所有圖表同步更新。

### 12-2-4　輿情問答

以自然語言提問，例如「最近大家對音波拉皮的評價如何」。系統回傳：

- **回答**：綜合檢索到的文章生成。
- **重點摘要**：條列式要點。
- **行銷建議**：給行銷人員的具體行動建議。
- **信心水準**：high／medium／low。
- **參考來源**：實際被引用的文章，可點選檢視原文。

相同問題於 15 分鐘內再次提問會回傳快取結果；可點選「重新生成」強制重新查詢。

### 12-2-5　關鍵字報表

輸入關鍵字後產生完整分析報告，包含聲量、情緒分佈、關鍵詞與洞察建議。報告會自動存入「分析歷史」。

### 12-2-6　監測與預警

新增欲長期追蹤的關鍵字，可隨時啟用或停用。當某關鍵字的負面比例超過設定門檻且文章數達下限時，系統自動產生預警。預警可標記為已讀。

### 12-2-7　爬取管理（管理員）

選擇平台與看板後觸發爬取，進度透過 WebSocket 即時顯示。頁面下方列出歷史爬取紀錄，含新增、略過與過濾篇數。

> **注意**：Dcard、Mobile01 與 Threads 會開啟瀏覽器視窗，屬正常現象，請勿關閉。

### 12-2-8　使用者管理（管理員）

新增使用者、指派角色（管理員／一般使用者）與訂閱方案、停用或刪除帳號。

### 12-2-9　系統設定（管理員）

調整爬取時間、頁數、預警門檻與各平台開關，並可檢視稽核紀錄（登入失敗、密碼變更、觸發爬取等）。

### 12-2-10　個人資料

檢視帳號資訊、變更顯示名稱與頭像、變更密碼。**變更密碼後，其他裝置上的登入階段會立即失效**，需重新登入。
